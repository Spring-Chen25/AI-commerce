# 从零看懂这套后端代码 · 小白学习指南

> 这份文档假设你**几乎没写过后端**。不用怕，我们不用一上来讲术语，而是用「开一家餐厅」的比喻，把每个文件夹、每行核心代码讲成人话。
> 看完你将能回答三个问题：① 这套代码在干什么？② 一个请求从浏览器进来后走了哪些地方？③ 我要加一个新功能该动哪几个文件？
> 进阶阅读：`开发文档.md`（讲 API、配置、每个工具怎么调用）。

## 第 0 章：先把心放肚子里

这套代码看起来文件夹很多，但它现在的状态是——**一个「空厨房」**。

- 锅碗瓢盆（数据库连接、日志、异常处理、登录、防重复提交……）全都**准备好了**；
- 但**一道菜都还没做**（没有商品、没有订单、没有任何业务功能）。

为什么要先准备空厨房？因为团队里 6 个人要各做各的模块（选品、补货、预测……），如果每个人都自己买一套锅碗瓢盆，又会乱又不统一。所以先把公共的东西备好，大家直接来炒菜就行。

**记住这句话**：这套代码 = 一个装修好、通了水电、摆放好厨具，但还没开始做菜的厨房。

## 第 1 章：用「餐厅」比喻，一眼看懂每个文件夹

想象你开了一家餐厅：

| 代码里的名字 | 餐厅里的角色 | 它干什么 |
|---|---|---|
| `main.py` | 餐厅大门 + 经理 | 客人从这里进来；经理负责开门营业、打烊、安排谁干活 |
| `routers/`（路由层） | 服务员 | 接待客人，问「您要什么」，把需求记下来交给厨房 |
| `schemas/`（数据模型） | 点菜单格式 | 规定点菜单长什么样（要几份、什么口味），不符合格式直接退回 |
| `services/`（业务层） | 厨师 | 真正做菜的地方：这一步放盐还是放糖，是业务规则 |
| `dao/`（数据访问层） | 配菜员 | 去仓库（数据库）拿食材、放食材，只管存取 |
| `models/`（ORM 模型） | 仓库货架标签 | 规定食材在仓库里怎么摆放（表的结构） |
| `utils/connectors/`（连接器） | 各种供应商电话 | MySQL、Redis、MinIO 这些「外部仓库/服务」的联系方式，需要时打电话 |
| `exceptions/`（异常） | 投诉处理台 | 出错了统一在这里处理，返回给客人一个友好说法，而不是把后厨的锅碗瓢盆摔给他看 |
| `utils/`（工具层） | 各种小工具 | 记日志的摄像头、发工牌(JWT)的前台、防重复下单的章(幂等)、记账本(审计) |
| `config.py` + `.env` | 配置清单 | 餐厅地址、仓库密码、营业时间……都写在这，改这里就能换环境 |
| `logs/` | 监控录像 | 每天发生的事都记下来，出问题可以回看 |
| `migrations/` | 仓库改造记录 | 货架要改结构时，记一笔「哪天加了什么」，可以随时回退 |

**分层的好处**：服务员不用会做菜，厨师不用去仓库搬货。每个人只干一件事，代码就不会乱成一团。将来要换仓库（比如 MySQL 换成 PostgreSQL），只改连接器，厨师完全不用知道。

## 第 2 章：一个请求是怎么走的？（最重要的一张图）

假设用户在浏览器里访问 `http://你的地址/health`，发生了什么：

```
  用户浏览器
      │  ① 发出 HTTP 请求
      ▼
┌─────────────────────────────────────────┐
│  main.py（经理/大门）                     │
│  ② 门卫检查：给请求盖个 request-id 章     │  ← access_log 中间件
│  ③ 记账本记一笔（如果是写操作）           │  ← 审计中间件
│  ④ 防重复提交检查                        │  ← 幂等中间件
│  ⑤ 跨域检查（能不能从这个网站访问）       │  ← CORS 中间件
└─────────────────────────────────────────┘
      │  ⑥ 交给服务员
      ▼
┌─────────────────────────────────────────┐
│  routers/（服务员）                      │
│  ⑦ health.py 里的 health() 函数接待       │
│     (业务请求会转给 service → dao → 数据库)│
└─────────────────────────────────────────┘
      │  ⑧ 处理结果
      ▼
┌─────────────────────────────────────────┐
│  统一包装（schemas/common.py 的 ok()）    │
│  ⑨ 把结果装进信封：{code, message, data}  │
└─────────────────────────────────────────┘
      │  ⑩ 原路返回
      ▼
  用户浏览器看到 JSON
```

**如果中途出错了呢？**（比如找不到资源、参数写错）

```
  任意一层抛出 AppException
      │
      ▼
  exceptions/handlers.py（投诉处理台）
      │  统一转成 {code: 404, message: "资源不存在", data: null}
      ▼
  用户看到友好错误，而不是一堆看不懂的报错堆栈
```

**这就是这套代码最核心的两条路**：正常走「请求 → 中间件 → 路由 → 包装 → 返回」；出错走「异常 → 投诉台 → 友好错误」。

## 第 3 章：从第一行代码读起（建议阅读顺序）

不要从 `main.py` 第一行开始死磕。按这个顺序读，你会越读越顺：

### 第 1 步：先看门口长什么样 → `main.py`

只看这 4 块，其他先跳过：

1. `lifespan` 函数：服务**启动时**干什么（连接所有外部服务），**关闭时**干什么（断开）。
2. `app = FastAPI(...)`：创建这个网站服务。
3. `app.add_middleware(...)`：门口装了哪些检查（门卫、记账、防重复、跨域）。
4. 最后两行 `register_exception_handlers(app)` 和 `register_routes(app, ...)`：把「投诉处理」和「服务员」接进来。

**一句话**：main.py 自己几乎不干活，它只是把所有零件**组装**起来。

### 第 2 步：看配置清单 → `.env` 和 `config.py`

`.env` 里是明文配置（真实密码都在这，**千万别发给别人**）。你会发现长这样：

```ini
DATABASE_URL=postgresql+psycopg://postgres:123456@120.46.149.36:5432/ai_ecommerce
REDIS_URL=redis://:123456@120.46.149.36:6379/0
```

`config.py` 把这些文本读成 Python 变量（如 `settings.REDIS_URL`），全项目都从这里取配置。

**小白要懂的一点**：为什么密码里有个奇怪的 `%40`？因为密码 `Root@123456` 有个 `@`，直接写在网址里会让程序看不懂（它以为 `@` 后面是主机名），所以要转义成 `%40`。这是网址的规矩，不是这套代码的规矩。

### 第 3 步：看服务员 → `app/routers/health.py`

这是最简单的路由，只有两个函数：

- `/health`：回答「我还活着吗」——进程在就返回 ok。
- `/ready`：回答「我依赖的外部服务都连上了吗」——会挨个问 MySQL、Redis 等。

### 第 4 步：看工具箱 → `app/utils/connectors/`

这里每一个文件负责连一种外部服务。以 `redis.py` 为例，你只需要看懂三件事：

- `enabled`：配置填了没？没填就当它不存在。
- `connect()`：真正去连接（第三方库在这一刻才导入，所以没装库也不会一启动就崩）。
- `_do_health()`：怎么检查它还活着（Redis 就是 ping 一下）。

### 第 5 步：看投诉台 → `app/exceptions/`

`base.py` 定义各种错误类型（找不到=404、没权限=401……），`handlers.py` 规定每种错误返回什么。

按这 5 步读完，你就已经理解 80% 了。剩下的 `dao`、`services`、`models` 现在是空的——因为业务还没开发。

## 第 4 章：必须知道的几个「黑话」

| 黑话 | 人话解释 |
|---|---|
| **API / 接口** | 一个可以被访问的网址，比如 `/health`。前端调它来拿数据。 |
| **请求 / 响应** | 请求 = 用户发过来的问题；响应 = 服务器回的答案。 |
| **路由（Router）** | 一张「网址 → 处理函数」的对照表。 |
| **中间件（Middleware）** | 请求进来和响应出去时，路上经过的关卡（检查、记账、防重复）。 |
| **异步（async/await）** | 等外部服务（比如连数据库）时，不傻站着等，先去处理别的请求，效率高。代码里看到 `async def` 就是异步函数。 |
| **连接器（Connector）** | 封装好的「连某个外部服务的电话本」，业务代码直接拿来用，不用重复写连接逻辑。 |
| **ORM / 模型（Model）** | 用 Python 类来表示数据库里的表，操作类就等于操作表，不用手写 SQL。 |
| **迁移（Migration）** | 数据库表结构的「版本记录」，改表结构像改代码一样有据可查、可回退。 |
| **JWT / 令牌** | 登录成功后发的一个「电子工牌」，之后带着它就能证明身份。 |
| **幂等** | 同一个请求点两次，只生效一次（防止手抖重复下单）。靠请求头 `Idempotency-Key` 实现。 |
| **日志（Log）** | 系统运行日记，出问题时靠它破案。 |
| **localhost:8000** | 本机的服务地址。`127.0.0.1` 就是「这台电脑自己」。 |

## 第 5 章：动手试一试（超简单）

### 5.1 把它跑起来

```bash
# 1. 进入目录
cd ai_ecommerce

# 2. 安装依赖（第一次需要，比较慢）
python -m pip install -r requirements.txt

# 3. 启动
python main.py
```

看到一堆日志，最后服务停在 8000 端口，就成功了。

### 5.2 用浏览器验证

打开这两个网址：

- `http://127.0.0.1:8000/health` → 看到 `{"code":200,"message":"success","data":{"status":"ok"}}`
- `http://127.0.0.1:8000/docs` → 看到自动生成的接口文档网页（可以点点看）

### 5.3 观察日志

打开 `logs/app.log`，你会看到刚才访问被记了下来，还带一个 `request-id`。这就是「监控摄像头」在工作。

### 5.4 看懂连接器状态

启动日志里会有类似：

```
connector[mysql] connected          ← MySQL 连上了（真实地址可达）
connector[redis] init failed: ...   ← Redis 没连上（可能没装 redis 库）
```

**没连上不用慌**：这套代码设计成「连不上也不崩溃」，只是对应功能暂时不可用。装上依赖、确认地址能通，重启就好。

## 第 6 章：我要加一个新功能，该动哪些文件？

用「加一个商品列表接口」当例子(角色对应第 1 章的餐厅比喻)：

| 步骤 | 文件 | 写什么 |
|---|---|---|
| 1 | `models/product.py` | 定义商品表长什么样（id、名字、价格）——**货架标签** |
| 2 | `models/__init__.py` | 加一行导入，让迁移工具认识它——**登记新货架** |
| 3 | `schemas/product.py` | 定义返回给前端的数据格式——**点菜单格式** |
| 4 | `dao/product.py` | 写「查所有商品」的数据库操作——**配菜员去仓库拿货** |
| 5 | `services/product.py` | 写业务逻辑（比如过滤下架商品）——**厨师做菜** |
| 6 | `routers/product.py` | 写 `/products` 接口，调用 service——**服务员接单** |
| 7 | `routers/__init__.py` | 注册这个新路由——**告诉经理新服务员上班了** |
| 8 | 命令行 | `alembic revision --autogenerate` + `alembic upgrade head` 建表——**改造仓库** |

记住这个顺序：**模型 → 数据格式 → 存取 → 业务 → 接口 → 注册 → 建表**。数据从最底层一层层往上冒，最后到用户眼前。

> 具体每行代码怎么写，看 `开发文档.md` 第 5 章。

## 第 7 章：常见困惑解答

**Q：为什么文件夹这么多，感觉好复杂？**
A：这是「分层架构」，故意的。现在觉得多，是因为还没有业务代码。等真正开发时，你会发现要改哪个文件一目了然，不会在一大坨代码里迷路。

**Q：连接器显示 error，是不是程序坏了？**
A：不是。这套代码故意「连不上也照常启动」。error 只是告诉你某个外部服务暂时没连上。看 `logs/app.log` 或启动日志的具体原因即可。

**Q：`.env` 和 `.env.example` 有什么区别？**
A：`.env.example` 是模板（占位符），可以提交给大家看；`.env` 是真实配置（含密码），被 `.gitignore` 忽略，永远不会上传。你复制模板改成自己的 `.env`。

**Q：改了配置为什么没效果？**
A：配置在程序启动时读一次就缓存住了。改完 `.env` 要**重启服务**。

**Q：我想本地快速跑，但连不上那些服务器怎么办？**
A：把 `.env` 里用不到的连接项**留空**，它们会自动变成 `disabled`（未启用），不影响启动。数据库可以临时改成 SQLite：`DATABASE_URL=sqlite:///./ai_ecommerce.db`。

**Q：出错时看到的是英文报错，正常吗？**
A：正常的报错（404、参数错误等）会被「投诉台」转成中文友好提示；但控制台日志里会有英文技术细节，那是给程序员看的，不用怕。

## 第 8 章：学习路线建议

```
① 跑起来，看到 /health 返回 ok        ← 建立信心
        ↓
② 读第 1 章的餐厅比喻，记住分层          ← 建立心智模型
        ↓
③ 按顺序读第 3 章的 5 个文件             ← 熟悉骨架
        ↓
④ 对着第 4 章黑话表，扫盲术语            ← 补齐词汇
        ↓
⑤ 照第 6 章加一个最简单的接口            ← 动手实践
        ↓
⑥ 遇到细节问题，查 开发文档.md           ← 查阅手册
```

**最重要的心态**：不要试图一次看懂所有代码。先跑起来、先能改一个接口，理解是一点点积累的。这套代码结构很干净，等你熟悉了，会觉得它很有条理。
